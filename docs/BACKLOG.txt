new feature ideas, scope changes, open questions and decisions taken during development.

### B-20 — Level of gh compatibility (umbrella decision)
Type:     decision
Status:   accepted -> §1.4
Added:    2026-11-13
Phase:    before Phase 0

Context:
- §1.1 says "comparable to gh"; product goal is to be a gh alternative, so
  users, scripts and coding agents should be able to switch with minimal
  relearning.
Proposal / options:
- Commit to a written compatibility policy in docs/compatibility.md:
  - Same command/subcommand names and flag names as gh wherever the
    Forgejo feature exists (e.g. `pr create --base/--head/--fill/--draft`,
    `issue list --state/--label/--assignee/--limit`, `-R/--repo`, `--web`).
  - Same `--json <fields>` / `--jq` / `--template` behaviour and, where
    possible, the same JSON field names as gh (`number`, `title`, `state`,
    `author.login`, `url`, `headRefName`, ...).
  - Same exit-code meanings as gh (B-11), extended only above gh's codes.
  - Same env-var model with FJO_ prefix (GH_TOKEN->FJO_TOKEN,
    GH_HOST->FJO_HOST, GH_REPO->FJO_REPO, GH_PAGER->FJO_PAGER,
    GH_PROMPT_DISABLED->FJO_PROMPT_DISABLED) and honour NO_COLOR,
    CLICOLOR_FORCE, PAGER, EDITOR/VISUAL.
  - Every intentional difference from gh is listed with a reason.
- Maintain a parity table (gh command -> fjo status: done / planned /
  not applicable on Forgejo / different semantics).
Decision:
- 2026-11-13: Maximum gh compatibility where Forgejo allows it (user: "alternative to gh, but for Forgejo"; explicit choice left to Claude, recommended option taken). Forgejo semantics win where they differ; every deviation documented in docs/compatibility.md. Exit codes follow from this -> B-11 option B (table to be finalized in Phase 0).

### B-1 — Replace Viper with plain YAML + own precedence logic

Added:    2026-11-13
Phase:    before Phase 0

Context:

Proposal / options:
- A) Drop Viper; use a YAML library + application-owned precedence
     (flag > env > repo-local > user > default), fully unit-tested.

Decision:
- 2026-11-13: A) Viper dropped. YAML library + application-owned precedence (flag > env > repo-local > user > default). Reason: hostnames as map keys must work; fewer dependencies; fully unit-testable.

### B-2 — `--json` flag semantics
Type:     decision
Status:   accepted -> §1.4, §5.1, §10.2
Added:    2026-11-13
Phase:    before Phase 0

Context:
- §5.1 says bare `--json` returns the default object, §10.2 shows
  `--json number,title,state`. With pflag optional values (NoOptDefVal)
  the space-separated form parses `number,title,state` as a positional arg;
  only `--json=number,title` works.
Proposal / options:
- A) `--json <fields>` always requires fields (gh behaviour); bare `--json`
     prints the list of available fields.
- B) Separate `--format json` + `--fields a,b,c`.
- Recommendation (B-20, gh alternative): A.
Decision:
- 2026-11-13: A) gh semantics: `--json <fields>` requires fields; bare `--json` fails with the list of available fields. `--jq` and `--template` require `--json`. Reason: gh compatibility (B-20).

### B-3 — Canonical host identity
Type:     decision
Status:   accepted -> §6.2
Added:    2026-11-13
Phase:    before Phase 0

Proposal / options:

Decision:

### B-36 — Redactor masks ordinary words after "token"
Type:     tech-debt
Status:   done
Added:    2026-11-13
Phase:    Phase 2 (before more user-facing messages mention tokens)

Context:
- internal/logging/redact.go: the bare-credential rule
  `(?i)\b(token|bearer)\s+[A-Za-z0-9._~+/=-]{8,}` treats any word of 8+
  characters after "token" as a secret. "no token provided" was printed as
  "no token REDACTED"; the message was reworded to "no token was provided"
  (Phase 1), which only works around this one case. Future errors such as
  "token required" / "token rejected" / "token settings" hit it too.
Proposal / options:
- A) Require a credential-like value: at least one digit and length >= 20
  (Forgejo PATs are 40 hex; JWT/bearer values are long and mixed).
- B) Match bare "token X" only in HTTP-ish contexts (after "Authorization",
  in debug HTTP traces) and rely on registered exact secrets otherwise
  (FJO_TOKEN and stored tokens are already registered with the redactor).
- Either way add regression tests with plain English phrases next to the
  existing secret-shaped cases.
Decision:
- 2026-11-13: applied option A to the bare "token/bearer <value>" rule:
  redact only values of at least 20 characters that contain a digit (real
  Forgejo PATs are 40 hex; exact secrets are registered separately). The
  Authorization-header and `token=`/`password=` rules still redact
  unconditionally, and a JWT-shape rule was added. Regression tests keep
  plain English ("no token provided", "token required", "token settings")
  intact while secret-shaped values are still masked.

### B-37 — 40-hex redaction rule also masks git commit SHAs
Type:     tech-debt
Status:   implemented in Phase 3c
Added:    2026-11-13
Phase:    Phase 3 (before PR/commit/checks output goes through the redactor)

Context:
- internal/logging/redact.go redacts every `\b[0-9a-f]{40}\b` because
  Forgejo PATs are 40 lowercase hex. SHA-1 commit IDs have the same shape, so
  error messages and debug logs that mention a commit (pr checks, merge
  conflicts, git errors) will show [REDACTED] instead of the SHA.
- Normal stdout output is not redacted, only errors and diagnostics.
Proposal / options:
- A) Drop the shape rule and rely on exact registration (every token fjo
  reads is already registered with Redactor.Add) plus the context rules.
- B) Keep it only in debug HTTP traces (headers/bodies), not in error
  messages.
Decision:
- 2026-11-16: A) Drop the 40-hex shape rule. Every token fjo reads is
  registered with Redactor.Add, and the Authorization, `token=` and JWT rules
  stay. Implement before 3c (pr checks/merge). Add a regression test: a
  SHA in an error stays visible and a registered 40-hex token is still masked.

### B-47 — `pr view <branch>` falls back to closed or merged PRs

Type:     enhancement
Status:   deferred
Added:    2026-11-17
Phase:    after Phase 3

- Branch resolution (also for `pr diff`/`pr checks` and no argument) only
  searches open PRs. gh falls back to the most recent closed or merged PR

### B-31 — Forgejo-specific semantics to respect (not GitHub)
Type:     tech-debt
Status:   verified for Phase 3; release part open (Phase 4)
Added:    2026-11-13
Phase:    Phase 3 / Phase 4

Context:
- PRs are issues in Forgejo: `issue list` must send `type=issues`.
- Draft PRs are a WIP title prefix (`WIP:` / `[WIP]`), not a state:
  `pr create --draft` / `pr ready` = title edit.
- Issue/PR `index` (number) vs internal `id` — CLI uses index.
- Release asset upload is multipart/form-data: stream via io.Pipe +
  multipart.Writer; size limit unknown to client -> map HTTP 413 to clear error.
- Commit statuses API backs `pr checks`.
- Verify each against pinned swagger (B-8).
Decision:
- 2026-11-16: verified against forgejo-v15.0.11.json and forgejo-v17.0.1.json:
  - GET /repos/{o}/{r}/issues has `type`, so `issue list` always sends
    type=issues. Filters available on both: state, labels, milestones, q,
    created_by, assigned_by, mentioned_by, since, before.
  - Pulls: list (state, sort, milestone, labels, poster; base/head only in
    17 -> B-44), /pulls/{index}.{diffType}, /files, /reviews,
    /pulls/{base}/{head}, /merge (GET = merged?, POST, DELETE) all exist.

    allow_rebase_explicit, allow_fast_forward_only_merge are what decides
    the allowed methods.
  - Issue pin/unpin (POST/DELETE /issues/{index}/pin) exists in both.
  - Commit status: /commits/{ref}/status (combined) and /statuses/{sha}.
  - Draft = WIP title prefix; CLI uses index everywhere. Release upload
    (Phase 4) still to verify then.
